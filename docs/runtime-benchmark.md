# Forward-model and filter runtime benchmark

`scripts/benchmark_runtime.py` compares the public Python API, direct PyO3
bindings, and native Rust calls on identical synthetic inputs. It prints a
terminal table and writes a summary CSV, raw timing CSV, and JSON metadata.
No ADX, KOGS, database, or antenna access is required.

Build both release artifacts from the repository root before running:

```bash
uv sync
uv run maturin develop --release
cargo build --release --locked --manifest-path crates/forward-models/Cargo.toml --example benchmark_runtime
.venv/bin/python scripts/benchmark_runtime.py --csv output/runtime-benchmark/runtime.csv
```

Use the venv Python directly after building: another environment synchronization
may replace the installed extension. The script checks its SHA256 against the
local release library; the native runner also rejects a debug build. The runner
currently expects this repository's Linux layout and default Cargo target directory.

The defaults are **2,500 observations, a 600-second span, three warm-ups, and
25 measured repetitions**. Select cases or change the workload explicitly:

```bash
.venv/bin/python scripts/benchmark_runtime.py \
  --case full_state_estimated_drag --case ukf_update --case ekf_update \
  --samples 2500 --duration-s 600 --repeats 25 --warmups 3 \
  --csv output/runtime-benchmark/selected.csv
```

`--help` lists every case. `--case` is repeatable; without it all 22 cases run.
The summary and `.samples.csv` are checkpointed after each case. The
`.metadata.json` includes the selected and completed cases, exact shared fixture,
source revision and working-tree status, binary hashes, dependency versions,
and the satkit data directory. Output files at the requested path are replaced.

## Workloads

| Cases | Timed result |
| --- | --- |
| `sgp4`, `sgp4_augmented`, `sgp4_epoch` | Whitened residuals and complete Jacobian, with 8/10/11 columns |
| `full_state`, `full_state_augmented` | Whitened residuals and complete Jacobian, with 7/9 columns |
| `full_state_fixed_drag`, `full_state_estimated_drag` | Augmented full-state evaluation with fixed/fitted Cd A/m, with 9/10 columns |
| `sgp4_states`, `full_state_states`, `full_state_states_drag` | N × 6 GCRF states |
| `{ukf,srukf,ekf}_construct` | One filter constructor |
| `{ukf,srukf,ekf}_predict` | N sequential predictions |
| `{ukf,srukf,ekf}_update` | N sequential updates, including automatic prediction |
| `{ukf,srukf,ekf}_snapshot` | N state snapshots |

Residual/Jacobian APIs calculate both together. Thus the default estimated-drag
case measures the complete evaluation producing a **2500 × 10 Jacobian**:
six Cartesian corrections, measurement-clock offset, center-frequency offset,
one pass bias, and Cd A/m. It does not claim to isolate Jacobian assembly.
Trajectory cases use the production batch sampling path. STM integration is
retained for numerical compatibility, while unused step STMs, matrix inversions,
and repeated whole-trajectory validation are omitted. See
[satkit-optimization.md](satkit-optimization.md) for before/after verification.

The fixture uses the existing ISS test TLE, one receiver at 63° N / 10° E /
0 m, and a 400 MHz carrier. The Cartesian state is initialized from that TLE
at its epoch. Samples start one second later, leaving room for centered time
derivatives; their spacing is `duration_s / (samples - 1)`. Epochs are normalized
to a stable satkit round trip before serialization, with exact JSON floating-point
round trips. Microsecond quantization may slightly perturb the nominal spacing.
Receiver coordinates likewise use the geodetic values returned by satkit,
including its nanometer-scale altitude roundoff, so every layer receives the
same station rather than independently reconstructing its nominal coordinates.
Drag cases use Cd A/m = 0.02 m²/kg with the production force-model settings.
These are synthetic model workloads, not visibility-selected contact predictions.

Filter observations are generated by the production augmented SGP4 model with
true `[time offset, bias, frequency offset] = [0.3 s, 7 Hz, 5000 Hz]`, plus
1 Hz Gaussian noise using NumPy seed 2026. Filters start at zero with covariance
`diag(4, 100, 1e8)`, zero process noise, observation variance 1 Hz², and no
innovation gate. Every repetition creates a fresh filter outside the timer,
except the constructor case where creation itself is timed. Gated rejection,
controller orchestration, and fitting entire orbit solutions are separate workloads.

## Timing and interpretation

All three layers validate complete outputs before timing: residuals, Jacobians,
trajectories, and final filter state/covariance. Update parity also checks accepted
counts and final NIS. Shape, finiteness, and numerical mismatches fail the run.
Parity uses relative tolerance 1e-9 and absolute tolerance 1e-7.
Inputs, validation, process startup, warm-ups, and file I/O are outside the timer.

| Layer | Included work |
| --- | --- |
| `python` | Public wrapper validation, conversion, binding, numerical work, and returned result construction |
| `pyo3` | Direct extension call with prepared Python inputs; binding conversion, Rust input construction/validation, numerical work, and Python result construction |
| `rust` | Existing core functions with prepared Rust inputs; native validation, numerical work, and native returned results |

Python uses `perf_counter_ns`; Rust uses `Instant` and consumes results through
`black_box`. Rust retains native matrices until after timing; JSON serialization
is never timed. For filter passes, Python/PyO3 timings include their Python
iteration loop and Rust timings include a Rust loop. These costs are part of
the measured application overhead. No empty-loop subtraction is applied.

The two Python layers share a process; Rust runs in a persistent subprocess.
Calls are serial, and layer order rotates each repetition. Each layer uses normal
warm frame caches, with no cache clearing between calls. The script sets
`SATKIT_DATA` to the installed Python satkit data directory unless explicitly set,
so both processes use the same reference-data location. Keep the data fixed and
avoid other CPU-intensive work while measuring.

The table reports sample mean, sample variance (**ms²**, denominator `n−1`),
standard deviation, and the Student-t confidence interval for the mean:

`mean ± t(0.975, n−1) × standard_deviation / sqrt(n)`

The sample size is the number of complete repetitions, not observations within
a pass. The CSV also includes operation count and derived mean microseconds per
operation. It is an average over the pass, not a per-update latency distribution.
All measurements are retained; no outliers are trimmed. Confidence intervals
assume independent repetitions and may understate uncertainty from correlated
machine load. This is not a test of statistical significance between layers.

`ratio_to_rust` and `overhead_ms` compare layer means against the Rust mean.
Differences include marshaling, allocations, validation, iteration, and runtime
noise. Small negative estimates are retained rather than clamped. Compare Python
with PyO3 to assess wrapper overhead, and PyO3 with Rust to assess binding and
representation overhead. The measurements alone do not identify Rust hotspots.

For a quick integration check:

```bash
.venv/bin/python scripts/benchmark_runtime.py --samples 8 --duration-s 60 \
  --repeats 2 --warmups 0 --csv /tmp/runtime-smoke.csv
.venv/bin/pytest -q tests/test_runtime_benchmark.py
```

The test suite's real three-layer smoke test skips if the release runner has
not been built; statistics and argument-validation tests remain available.
